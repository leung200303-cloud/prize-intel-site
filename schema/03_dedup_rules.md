# 去重規則 v1.0（Step 2 交付）

> 對象：同一款景品喺多個站以唔同標題出現，要收斂成 `item` 一筆。
> 對應 schema：[01_schema.sql](01_schema.sql)

---

## 0. 點解難 — 三個現實

1. **大部分プライズ 冇印 JAN 喺貨上**。JAN 只喺一番くじ／一般販售可靠，夾機景品多數冇。所以 JAN 唔可以係唯一主鍵。
2. **每個站自己作標題**。同款貨：
   - bsp-prize：`【鬼滅の刃】冨岡義勇 MAXIMATIC フィギュア`
   - コレトレ：`【鬼滅の刃】冨岡義勇のMAXIMATICフィギュアがオンクレに登場！`
   - にじめん：`『鬼滅の刃』冨岡義勇の最新プライズが登場`
   三段字面相似度可以低到 0.4，但其實係同一件。
3. **同角色同月同系列可以有 vol.1 / vol.2**。呢個係最危險嘅誤併來源——唔止重複，係**兩件唔同貨合併成一件，行情直接錯**。

---

## 1. 資料流

```
抓取 → 抽欄位 → 正規化 → L1 JAN → L2 複合指紋 → L3 trigram 模糊 → 落庫
                                    ↓              ↓
                              命中即自動合併   只入 merge_candidate 隊列
```

原則：**寧願漏合併（留兩筆，人手執），都唔好誤合併（行情錯，場主信錯）**。
所以自動合併只有 L1、L2 兩層，而且 L2 有硬性前置條件（見 §3）。

---

## 2. L1 — JAN 精確匹配

| 項目 | 規則 |
|---|---|
| 觸發 | 新貨有 `jan_code`，而且 DB 已有同 JAN 嘅 item |
| 動作 | **直接自動合併**，掛新 `item_source` |
| 保證 | `uq_item_jan` partial unique index，確保一 JAN 只有一筆 |
| 覆蓋率 | 估計 20–35%（一番くじ／一般販售為主） |

冇 JAN 就落 L2。

---

## 3. L2 — 複合指紋

```
fingerprint = sha256(
    maker | brand_line | ip_work | primary_character_id
    | release_month | normalize(series_group) | round(size_cm/5)*5
)
```

**唔含標題**。呢個係關鍵設計：標題差異唔影響命中。

### 自動合併嘅硬性前置條件

L2 命中仲唔夠，要同時滿足先准自動合併：

| # | 條件 | 唔滿足點算 |
|---|---|---|
| 1 | 兩邊 `size_cm` 都唔係 NULL | 降級 L3（尺寸係最強區分訊號） |
| 2 | 兩邊 `ip_work_code` 相同（或其中一邊 NULL） | 降級 L3 |
| 3 | 兩邊 `series_group` 相同，或其中一邊 NULL | **降級 L3**（vol 差異風險） |
| 4 | 命中筆數 = 1（唔係一次中多筆） | 降級 L3 |

> 條件 3 係因為 `MAXIMATIC 鬼滅 vol.1` 同 `vol.2` 可能同角色同月。`series_group` 要由解析器抽 `vol.` / `弾` / `第N弾` / `Part N` 寫入，冇抽到就留 NULL → 降級人手判斷。

### 為咩指紋唔包 title
如果包標題，L2 就退化成 L3（標題一差異就唔中）。呢個係上一個版本嘅錯，已修正。

---

## 4. L3 — trigram 模糊比對

| 項目 | 規則 |
|---|---|
| 工具 | `pg_trgm`，`similarity(normalized_title_a, normalized_title_b)` |
| 撈候選門檻 | `>= 0.45` 且 `ip_work` 相同 且 `release_month` 相差 <= 2 個月 |
| 標記 | `>= 0.75` 標「高度疑似」；`0.45–0.75` 標「需查」 |
| 動作 | **寫入 `merge_candidate`**，`status='pending'`，永不自動合併 |
| 排序 | 人手按 `similarity DESC` 逐對覆核 |

⚠️ 注意：`pg_trgm` 對日文係以「字元 trigram」運作，唔係分詞。對短標題（<10 字）會偏高，所以要配合 `ip_work` + 月份窗口收窄，唔可以單靠 similarity。

---

## 5. 「同款多名」四種情況同處理

| 情況 | 例子 | 處理 | 自動化 |
|---|---|---|---|
| ① 標題裝飾差異 | `【】`、`★`、`！`、全形半形、片假名/平假名 | `normalize_title()` | ✅ 全自動 |
| ② 前後加廢話 | 「〜が登場！」「オンクレに登場」 | normalize 唔夠力 → 要靠 L2 | ✅ 靠指紋 |
| ③ 譯名／別名（中英日） | 義勇 / 冨岡義勇 / Giyu / 富冈义勇 | **入 `aliases`，只用嚟搜尋，唔參與 merge** | ⚠️ 半自動 |
| ④ 真正唔同款同名 | MAXIMATIC vol.1 vs vol.2 | `series_group` 閘 + 人手 | ❌ 人手 |
| ⑤ 再販 vs 初版 | 同款隔年再販 | 合併同一筆，`is_resale=true`，保留再販日期 | ✅ 規則化 |

③ 嘅重點：**譯名唔可以參與 merge 判斷**。否則「義勇」同「Giyu」會被當兩個角色，或者反過來把兩個唔同角色併埋。角色一律以日文原名做 key，譯名只做搜尋 alias。

---

## 6. 正規化做過乜（`normalize_title`）

| 步驟 | 動作 | 例 |
|---|---|---|
| 1 | 全形英數 → 半形 | `ＭＡＸＩＭＡＴＩＣ` → `maximatic` |
| 2 | 片假名 → 平假名 | `フリュー` → `ふりゅー` |
| 3 | 轉細楷 | `MAXIMATIC` → `maximatic` |
| 4 | 拆裝飾符號 | `【鬼滅の刃】` → `鬼滅の刃` |
| 5 | 壓空白 | `A   B` → `ab` |

**刻意唔做**：唔做同義詞替換、唔做翻譯、唔做 stem。呢啲交去 alias / 人手，避免規則互相打架。

---

## 7. 人手合併流程

1. 開 `merge_candidate` 待審隊列（`v_pending_merges` 可視圖化）
2. 逐對睇：標題、圖、發售月、尺寸、來源
3. 判斷：
   - 同款 → `status='merged'`，執行合併
   - 唔同款 → `status='rejected'`，**同時寫 `resolution_note`**（下次唔會再問同一對）
   - 唔確定 → `status='deferred'`
4. 合併執行規則：

```
survivor 優先次序：
  1. 有 JAN 嗰筆
  2. item_source 較多嗰筆（來源覆蓋廣）
  3. confidence 較高
  4. first_seen 較早
  5. id 較細（最終 tie-break，保證 deterministic）

合併時：
  - item_source 全部重掛去 survivor
  - item_character 去重合併
  - price_ref 重掛 → 跑一次 cap 清理（可能超 3 條）
  - aliases 合併（保留被併標題做搜尋 alias）
  - 寫 merge_log(layer, detail)
  - 被併 item 刪除（或標 soft-delete，建議軟刪一個月先硬刪）
```

**二人覆核**：第一個月全部人手覆核；穩定後只覆核 `similarity < 0.75` 嘅個案。

## 8. 驗收指標（Step 3 PoC 要量嘅數）

| 指標 | 定義 | 目標 |
|---|---|---|
| 自動合併率 | 自動合併數 / 總入庫數 | > 65% |
| 候選誤報率 | 人手判「唔同款」/ 候選總數 | < 25% |
| 漏併率 | 抽 100 對應同款但冇合併 | < 10% |
| 人手耗時 | 每對覆核平均秒數 | < 45 秒 |
| 重複殘留 | 同 JAN 出現兩筆 | **必須 0**（有 unique index 保證） |

Step 3 抽 30–50 款時，直接喺 `06_PoC抽樣模板` 加三欄量呢啲數：

- `相似度`（人手估 0–1）
- `L2 有冇命中`（Y/N）
- `耗時(秒)`

## 9. 已知限制（誠實講）

1. **冇 JAN 嘅貨，L1 完全幫唔到**，L2 靠解析器抽欄位質素。解析器抽唔到 `series_group` / `size` 就會大量降級人手。
2. **日文分詞**：`pg_trgm` 唔係真分詞器，長標題 OK，短標題偏差大。第二階段建議換 `pgroonga` 或 `pg_bigm`。
3. **跨語言**：中英譯名永遠唔會靠標題自動對上，只靠 L2 結構欄位。所以解析器要抽得準。
4. **圖片唔做 hash 比對**：現階段唔做（版權 + 成本）。如果 L1–L3 都做唔到，可以考慮後期加 perceptual hash 做第四層（只做候選，唔自動併）。
5. **同角色不同造型但同月同尺寸**（例如「義勇 通常版」vs「義勇 特別版」）→ 指紋會撞，靠 `series_group` 或人手。呢個係最難嘅 5%，唔好期望自動化。

## 10. 下一步接口

Step 3（A 方案：人手抽樣 30–50 款）要答嘅三條問題，直接餵返呢份規則：

1. **標題差異幾大？** → 決定 L3 門檻（0.45 定 0.55）
2. **L2 命中率幾多？** → 決定解析器要抽邊幾個欄位（尤其 `size_cm`、`series_group`）
3. **人手 merge 一對幾分鐘？** → 決定 Step 4 後台要唔要一整頁 merge UI，定係先寫 SQL 手動做
